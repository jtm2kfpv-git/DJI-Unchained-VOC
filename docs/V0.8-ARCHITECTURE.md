# v0.8 Advanced Recording Architecture

Status: **instant replay implemented and desktop-verified; hardware acceptance pending**

Baseline: **v0.7.4 hardware-tested alpha prerelease**

## Goals

v0.8 adds two lossless recording capabilities without changing the proven DJI USB, LogicLink,
H.264 decode or live-preview path:

1. **Instant replay** — retain a configurable recent window and save it after an event.
2. **Split recordings** — roll a long recording into independently playable, configurable parts.

Both features operate on the original compressed H.264 access units. They must not record the
screen, application controls or audio, and they must not add Android permissions.

## Instant replay design

- Replay is disabled by default and explicitly enabled by the user.
- Initial duration choices are 15, 30 and 60 seconds; 30 seconds is the initial selection.
- A hard 128 MiB memory ceiling protects the app and live USB path. At unusually high bitrates,
  the retained duration may therefore be shorter than the requested duration.
- The buffer stores cloned compressed access units, not decoded frames.
- A retained clip always begins at an IDR keyframe with SPS/PPS metadata.
- If limits evict the starting keyframe, dependent frames are discarded until the next usable IDR.
- **Save replay** takes an immutable snapshot so live buffering can continue while the clip is
  written.
- The first output target is a lossless MP4 in `Movies/DJI Unchained VOC`.
- The UI and diagnostics must show requested duration, actual retained duration, memory use,
  evictions, save state and dropped units.

At the validated stream rate of approximately 15.3 Mbit/s, 30 seconds of compressed video is
roughly 57 MiB before small Java-object overhead. The 128 MiB ceiling leaves useful headroom while
making 60 seconds practical at the measured rate.

## Split-recording design

- Splitting is disabled by default.
- Advanced settings provide quick choices and a custom duration in whole minutes.
- The accepted custom range is 1–60 minutes.
- Reaching the requested duration marks a split as due; the actual rollover occurs at the next
  usable IDR keyframe.
- The boundary keyframe becomes the first sample of the new part. It is never duplicated into the
  completed part.
- Every MP4 part gets a fresh monotonic timeline beginning near zero and its own SPS/PPS format.
- Raw H.264 parts begin with SPS, PPS and IDR bytes so each part is independently decodable.
- Part files use a shared session timestamp and a stable suffix such as `-part-001`.
- A failure to open or finalize the next part stops recording safely without blocking USB receive
  or live decode.
- Diagnostics report requested part duration, current part, completed parts, rollover delay,
  per-part bytes/units and any finalize/open failure.

## Pipeline boundary

```text
DJI USB -> LogicLink -> H.264 assembler -> live decoder
                                      |-> original recorder -> MP4/raw parts
                                      `-> replay buffer -> replay MP4 writer
```

The recorder and replay buffer are downstream consumers. Neither may apply backpressure to the USB
or decoder path. Bounded queues and immutable snapshots isolate slow storage from live video.

## Delivery stages

### Stage 1 — pure policy foundation

- memory- and duration-bounded, keyframe-aligned replay buffer
- keyframe-aware recording split policy
- deterministic unit tests without Android or hardware dependencies

### Stage 2 — replay integration

- feed the buffer from the existing assembled access-unit path
- add enable/duration controls and a large **Save replay** action
- write a snapshot as lossless MP4 on the recorder executor
- add schema 5 replay diagnostics

Implementation status: **complete in `0.8.0-dev`**. Hardware validation remains required before
the replay workflow is accepted for release.

### Stage 3 — split integration

- add part-duration controls
- refactor destination creation into a recorder-owned part factory
- roll MP4 and raw H.264 outputs on safe IDR boundaries
- expose part status and schema 5 split diagnostics

### Stage 4 — hardware acceptance

- confirm live preview remains stable with replay disabled and enabled
- save 15/30/60-second replay clips and decode every frame
- test a deliberately short development split interval, then normal minute-based settings
- verify every part starts independently and timestamps are monotonic
- test manual stop, disconnect, reconnect, low storage and app closure around a rollover
- compare recorder/replay drops and USB/parser health with the v0.7.4 baseline

## Release gates

- No regression in v0.7.4 live view, display modes, recording or recovery.
- No new Android permission.
- No unbounded memory or storage queue.
- No output begins before usable SPS, PPS and IDR data.
- All MP4 outputs decode without errors and have monotonic timestamps.
- Each split part plays independently.
- Replay and splitting cannot be active in a state the UI or diagnostics misreports.
- Root source and the eventual `versions/v0.8.0` snapshot match before publication.
